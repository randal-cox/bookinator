# Bookinator interface policy

Bookinator inherits the compact, inspectable application language used by
Wavinator and PD Doseinator. These are project-wide contracts rather than
screen-specific suggestions.

## Readable type

- User-facing explanatory prose, evidence, verdicts, and action labels use at
  least 12px type. Compact metadata and short captions may use 11px.
- Text below 11px is reserved for nonessential graphical labeling where space
  is intrinsic to the visualization; it may never carry the only explanation
  of a state, score, finding, or action.
- Dense interfaces earn compactness through hierarchy, disclosure, and layout,
  not by shrinking substantive text until it becomes difficult to read.

## Dialogs

- Application dialogs are movable and remain inside the viewport.
- The visible dialog heading is the drag handle and uses a move cursor.
- Interactive controls never begin a dialog drag.
- Escape closes ordinary dialogs; clicking the backdrop closes them when doing
  so cannot discard an irreversible operation.
- The close control remains in the upper-right corner.
- Primary and secondary actions stay grouped at the bottom-right.
- Dialog movement is implemented once by the shared `installMovableDialog`
  behavior. New dialogs opt into the standard automatically through
  `[role="dialog"]` inside a `.backdrop`.

## Intake actions

- Adding source material uses a dashed well, not a generic primary button.
- A compact well may open the relevant intake dialog from a toolbar or heading.
- Empty states use a larger well that explains what will happen.
- The full intake dialog contains the functional drag-and-drop target.
- Compact Add Text and Import wells retain drop behavior but use the same
  icon-above-word silhouette as neighboring toolbar commands. A dashed inset
  quietly communicates that files can be dropped without turning them into a
  different class of control.
- A well must remain keyboard accessible and describe its action without
  relying on the dashed border alone.

## Workspace button bars

- Book-specific actions live in the workspace button bar, before view tabs,
  instead of floating at the far edge of the book identity header.
- Actions and view tabs are separated visually: actions use the standard light
  button treatment; the active view uses the filled selection treatment.
- Workspace views use inator tool buttons: a consistent icon above one short
  word. Active views use the selected-tool treatment; commands remain actions.
- Do not duplicate global navigation in a workspace bar. The Books menu and
  standard browser history shortcuts provide the route back to the library.

## Library lists

- List columns with meaningful values are sortable from their headers. Sorting
  is stable UI state and never changes the underlying manuscript or book data.
- Every row has a selector. The header selector cycles none, a remembered
  partial selection, and all visible rows; its indeterminate appearance is a
  real third state rather than decoration.
- Selection-aware button-bar actions remain disabled until their required
  selection cardinality is satisfied.
- Row actions use compact icon buttons with accessible names. A book title and
  its pencil both open the workspace; identity editing lives in that
  workspace's button bar.
- Books use one operational table rather than parallel list and grid views.
  Queue membership, structural preparation, summary completion, ingestion time,
  and last analysis change are visible and sortable columns.
- The library pipeline is an explicit durable queue. Adding a book to it does
  not bypass chapter-map review; bulk Start prepares unmapped books for review
  and continues already reviewed books sequentially.
- JSON exports carry the selected books' complete saved analysis and provenance,
  but not their copyrighted PDF bytes. Imports restore analysis as local book
  projects and clearly report that no source PDF is attached.
- Global pipeline Start and Stop controls form the final, flush-right command
  group. Removal is always named “Remove from pipeline,” never merely “Remove.”

## Identity marks

- Books may use a short Unicode mark, an emoji, or a locally uploaded image.
- Text marks are limited by grapheme cluster rather than code unit so joined
  emoji and accented characters are not split. Up to three graphemes are kept.
- Image marks use the shared dashed drop target, prevent the browser's default
  file-navigation behavior, and are center-cropped to a small local WebP.
- An unset mark falls back to the first grapheme of the book title. The fallback
  is generated by Bookinator; it is not presented as manuscript metadata.
- During PDF intake, Bookinator may extract plausible artwork from the opening
  pages and ask the local intake model whether it is a book-specific mark. The
  model may refuse every candidate; only suggestions at or above the confidence
  threshold populate the preview, and the user always retains final control.
- The stored shape is shared across the project: `{ kind: "unicode", value }`
  or `{ kind: "image", value, width, height }`.
- Image marks are scaled to contain the entire source image. Bookinator may add
  breathing room around tall or wide artwork but must not crop it implicitly.
- Background color and book-outline treatment are independent presentation
  properties. Text and emoji default to an outlined book; uploaded images
  default to no outline. Editors may override both defaults.
- The outlined treatment includes both the outer cover silhouette and a visible
  vertical spine crease; it must remain legible on light and dark backgrounds.
- The spine is real layout, not an overlay on centered artwork. Text, emoji,
  and images are centered within the front-cover panel to the right of the
  crease. A restrained stack of pale page edges and a soft lower-right shadow
  gives outlined marks physical book depth without muddying small icons.
- The icon preview is also an image well. It accepts dropped image files and
  remains keyboard operable, while the larger labeled image well provides the
  explicit affordance for first-time users.

## Inspectable pipelines

- Long-running analysis exposes named stages rather than a single spinner.
- Structural preparation and model inference are separate user decisions. Page
  extraction and chapter detection produce a reviewable chapter map before the
  editor starts costly chapter summaries.
- While inference is active, the workspace names the model, the current
  chapter, and the fact that completed progress is saved. Model assignment is
  reachable beside the action that uses it.
- Every stage records status, useful counts, timestamps, and the assigned model
  where applicable. Chapter work additionally records page provenance and input
  size.
- Chapter detection is not complete merely because boundaries were found. The
  pipeline materializes one ordered, page-linked local object per section and
  exposes a “Saved chapter objects” stage with its verified count and relative
  archive location. Existing aggregate extractions are backfilled without a
  model rerun.
- Dossier source chunks are durable page-bounded artifacts, grouped under their
  conceptual chapter rather than replacing it. Adjacent chunks overlap by one
  source page, expose their exact PDF page range, and visibly distinguish saved
  source from pending or completed structured dossier work.
- ETA is computed from at most the five most recent timed chapters produced by
  the active reader model, multiplied only by unfinished chapters. The UI shows
  sample size, average chapter time, and remaining count so the estimate is
  inspectable rather than an unexplained clock.
- Completed chapter artifacts are written incrementally so interruption does
  not erase prior work. A server restart marks in-flight work as interrupted
  rather than pretending it is still running.
- Failures remain visible beside the stage or chapter that produced them and
  can be retried without disguising previous results.
- Transient local-model transport failures retry automatically. If repeated
  attempts still fail, only that chapter or chunk becomes retryable and the
  book continues; the whole-reader-stopped state is reserved for an actually
  interrupted server process. Worker ownership is persisted by process so a
  second local Bookinator server cannot falsely declare another server's live
  worker dead.
- A chapter is complete only when it contains a non-empty summary. Valid JSON
  with missing or variant fields is normalized when possible; an empty result
  is a visible retryable failure and never advances completed progress.
- Chapter reading shows aggregate completed/total progress and derives ETA from
  observed completed-chapter durations. Before the first sample it says that it
  is still estimating rather than inventing a duration.
- The chapter stack is a parallel progress display: a strong left rail and
  readable status pill distinguish completed green, running blue, pending
  neutral, and failed red. The chapter label owns its compact `pages 10–21`
  provenance; page range is never folded into completion status and does not
  assume that every manuscript began as a PDF.
- Chapter rows never change component type when reading begins. Every saved
  chapter is always a disclosure; pending rows contain a plain not-yet-done
  message, and completed rows reveal the summary in the same body location.
  A quiet eye button immediately before the chapter label always opens the
  canonical manuscript text without toggling the disclosure.
- Complete, Running, and Failed status pills expose the model, timing, input,
  retry, or failure details that produced that state. Those operational details
  are not a second disclosure competing with the chapter summary.
- Viewpoint and subchapter markers are navigation for the canonical manuscript,
  not summary decoration. The source reader lists them as ordered jump links
  and targets every repeated occurrence independently.
- Summary chapters and dossier chunks use one shared analysis-row component:
  source eye, inline page range, stable disclosure, status-triggered run details,
  and the same failure behavior. Dossiers link back to their complete canonical
  chapter rather than trapping the editor inside a processing chunk.
- Editorial result groups use one shared icon-heading treatment. Icons encode
  meaning rather than decoration: check for facts, arrow for events, target for
  entities, question mark for questions, diamond for promises, clock for
  timeline observations, and paragraph mark for evidence.
- Markdown is the canonical source format, not visible label punctuation.
  Heading markers such as `##` and `###` are stripped from chapter titles and
  viewpoint labels at ingestion, retrieval, and display boundaries.
- Stop closes the active streamed model response promptly and pauses the global
  worker. Completed chapters remain saved; the interrupted chapter returns to
  pending and Resume restarts it from the beginning. “Stopping” is transitional
  feedback, never a substitute for a finished paused state.
- Completed progress always describes the whole manuscript: every valid saved
  summary out of every chapter, including work preserved before Stop and
  Resume. Manuscript position (for example, section 7 of 26) is labeled
  separately and is never presented as a completed count.
- Book-level Start, Continue, Resume, Rebuild, and Restart actions move that
  work to the front of the durable global queue and start the global worker if
  it is off. Their controls use the standard inator icon-above-word treatment.
- When queued work exists, the top bar exposes whether the global pipeline is
  on or off and how many books are waiting. The indicator disappears when
  there is nothing actionable in the queue.
- Restart is destructive to the current visible summaries and always requires
  confirmation. Prior model, timing, and input records are archived per chapter
  before every chapter returns to pending.
- Changing the assigned chapter reader never silently rewrites existing work.
  When the open book has summaries, Bookinator offers an explicit fresh reading.
- Polling must not replace unchanged workspace markup. Chapter disclosure state
  and scroll position survive genuine pipeline updates; pending chapters stay
  collapsed until the editor opens them. Running work is indicated by a
  highlighted row and a RUNNING label; status changes never open a disclosure.
- Chapter detection rejects repeated heading candidates from front-matter tables
  of contents. Chapter lists remain in manuscript page order, never lexical
  title order.
- A chapter title is a label, not a sort key. Numeric, Roman-numeral, spelled,
  and free-text titles all receive a separate sequence derived from their PDF
  starting page. Every pipeline stage preserves that sequence.
- Structural chapter labels, authored chapter titles, and ordered viewpoint or
  subchapter markers are separate fields. Summary rows show the structural and
  authored titles; the source reader exposes viewpoint markers in manuscript
  order because viewpoint changes are meaningful book structure, not duplicate
  data.
